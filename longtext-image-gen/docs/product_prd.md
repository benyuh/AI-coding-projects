1. 背景
长文的阅读效率低，有较高的消费门槛。需要设计一个 Agent/Skill，以图（或视频）代文的方式，实现长文内容的高效率消费。

4. 分模块需求详述 【ai coding时核心关注】
4.1 多内容源处理 Agent 0
特殊情况预处理：当场景为AI搜场景，用户使用AI搜能力，获取的是全网多个信源的内容，即“长文”本身是多个内容源时，需要进行“多内容源处理”，否则可以跳过本步骤
4.1.1 信源类型分类

举例	处理优先级
政府公告、官方公告、SEC 文件、学术论文	最高
主流媒体报道(新华社、路透社、央视等)	高
行业专家博客、机构研报	中
普通网页、博客、论坛	低
评论、社交帖子	最低,仅作辅助

4.1.2 内容去重规则
两层去重:
第一层:语义去重(粗去重)
  对每个源做 200 字摘要 → 用 embedding 计算相似度
  相似度 > 0.85 的源,标记为 "duplicate_cluster",合并处理
第二层:句子级去重(细去重)
  在生成 claim 时,如多个源都包含同一论点
  → 不重复列出,而是在 evidence_span 字段记录所有支持源
强制规则:同一论点最多保留一份表述,但 evidence 必须保留全部来源(为后续溯源)。
4.1.3 冲突处理规则
冲突类型分类:

冲突类型	例子	处理策略
数字冲突	A 源说"增长 5.2%",B 源说"5.4%"	标注 data_disagreement,展示时取最权威源,但在 annotation 中说明分歧
时间冲突	A 源说"2024 年 3 月",B 源说"2024 年 4 月"	同上
事实冲突	A 源说"已通过",B 源说"未通过"	标注 factual_disagreement,展示时不选边,呈现"两种说法"
立场冲突	A 源支持,B 源反对	标注 perspective_disagreement,作为"观点分歧"卡片专门呈现
时效冲突	A 源是 2024 年数据,B 源是 2025 年数据	取最新源,但保留旧源作为历史对比

冲突处理优先级:
权威性优先级(从高到低):
  authoritative > mainstream_media > professional_blog > general_web > user_generated
时效优先级(同权威级内):
  最新发布 > 较旧发布(超过 6 个月差异时启用)
数量优先级(同权威级 + 同时效):
  多数源说法 > 少数源说法(至少 3 个源支持才生效)
关键规则:事实冲突永远不选边——哪怕只有一个源说不同,也必须保留分歧展示。
4.1.4 引用溯源规则
每个 claim 必须满足以下溯源要求:
- 任何 claim 至少有 1 个 source_ref,无源的 claim 直接驳回
- 数字、时间、人名、机构名必须可追溯到具体源(不允许"综合多源"模糊处理)
- 争议性内容必须用 controversy_preserved 方法,不允许悄悄选边
4.1.5 信息完整性补全
多源场景下经常出现"信息片段化"——某个关键事实在所有源中都没有提及。规则:

缺失类型	处理策略
关键背景缺失	不编造，标注背景信息有限
关键数据缺失	不编造,在卡片中明确显示"具体数据暂无公开信息"
关键时间缺失	不编造,显示"时间不详"

强制规则:严禁用 LLM 自身知识填补缺失——多源场景下 LLM 必须严格基于源,不补全。
4.1.6 长文封装
Agent 0 完成多源处理后，将聚合结果封装为统一的下游输入对象，并显式标记多源元信息，供下游模块识别。
4.2 信息预处理 agent1_router
4.2.1 文章类型识别规则
Router 在判定文章类型时,优先级从上到下，优先识别是否为多结果场景，如果判断为多结果场景，其余文章类型不需要识别。

优先级	类型	识别特征
P0	多结果	上游下发
P1	通知政策	出现"国务院/部委/通知/办法/条例/印发"等关键词,且文体为公文体
P2	分析研究	出现"摘要/Abstract/参考文献/方法论/样本量/研究表明",或来源域名为学术站点/券商研报
P3	热点事件	出现明确时间地点人物,且涉及具体事件;含多个媒体引用
P4	个人观点	第一人称比例 > 5%,或来源为博客/播客逐字稿
Default	other	以上均不匹配

实现备注:
- 识别能力由 LLM 输出，Router prompt 中明确给出上述匹配规则与示例，要求输出 JSON。
- 如果文章过长（超过3w字）、过短（少于200字）、无意义等，则直接跳过后续步骤，反馈原因，不走下游流程
4.2.2 用户画像识别规则

信号源	优先级	判定为专业用户	判定为普通用户
用户/上游主动设置	P1	已选"专业模式"	已选"通俗模式"
历史使用记录	P2	80% 以上输入为科研/研报类	80% 以上输入为热点/观点类
当前文章特征	P3	含 ≥ 5 个专业术语 + 文章类型为 research_paper	文章类型为 personal_opinion 或 news_event
默认	P4	不满足以上则默认普通	—

4.2.3 风险评估与拒绝规则
风险较高的内容， 拒绝处理或仅做有限处理:
内容类型
处理策略
法律文书、合同、判决书
拒绝转图。原因:法律文本去任何细节都可能造成误读
医疗诊断、用药指导
拒绝转图。原因:专业医疗信息删减后可能危害健康
诗歌、歌词、文学作品
拒绝转图。原因:艺术性损失过大 + 版权风险

拒绝转图。原因:隐私扩散风险

4.3 内容理解 agent2
4.3.1 长文分块规则
文本长度
分块策略
< 3000 字

3000-10000 字

4.3.2 卡片数量决策规则
- 基础规则:
  原文长度 < 1500 字   → 3-5 张卡片
  原文长度 1500-5000   → 6-10 张卡片
  原文长度 5000-15000  → 10-15 张卡片
  原文长度 > 15000     → 不超过 15 张 + 强制添加目录卡
- 调整规则(在基础规则上修正):
  + 信息密度高(数据点 / 千字 > 6)→ 卡片数 +2
  + 用户为专业用户 → 卡片数 +2(专业用户能消化更多卡片)
  - 用户为普通用户 → 卡片数 -2(避免过载)
  - 多源场景且存在 ≥ 1 个冲突 → 卡片数 +1(为冲突卡预留位置) 
  - 多源场景且 source_count > 5 → 卡片数 +1(增加"信源说明卡")
约束:无论怎么调整,卡片数最少 3 张(否则没必要做),最多 15 张(超过则用户不会看完)。

4.4 视觉策略调度agent4
4.4.1 判断内容结构
根据文章类型自动匹配叙事结构：

文章类型	内容结构
通知政策	结构 1:问题-机制-影响-行动(Problem-Solution-Action,P-S-A 框架)
	适用场景:有明确目标的政策(如"个税改革"、"新能源补贴方案")
	卡片骨架(6-8 张):
	
	[1] 一图概括:政策名称 + 一句话核心 + "和你有什么关系"钩子
	[2] 问题:政策要解决什么问题(为什么需要这个政策)
	[3] 机制:政策是怎么运作的(核心条款用大白话解释)
	[4] 影响 - 谁受益:利益相关方 A
	[5] 影响 - 谁受影响:利益相关方 B
	[6] 影响 - 普通人视角:对你日常生活的具体影响
	[7] 行动建议:你需要做什么 / 什么时候做 / 怎么做
	[8] 时间表 + 政策原文链接
	
	结构 2:对比变化(Before-After Comparison)
	适用场景:对原有政策的修订、新旧规则交替(如"新版税法 vs 旧版"、"医保政策更新")
	卡片骨架(5-7 张):
	
	[1] 政策概览 + 生效时间(强调"什么时候开始影响你")
	[2] 核心对比卡:旧政策 vs 新政策(并列展示)
	[3] 变化点 1:具体变了什么(数字 / 规则 / 流程)
	[4] 变化点 2:具体变了什么
	[5] (可选)变化点 3
	[6] 谁会感受到变化:具体到人群和场景
	[7] 过渡期安排 + 行动清单:旧规怎么收尾、新规怎么衔接
	
	视觉特征:
	
	核心对比卡用左右分栏或上下分栏,左灰(旧)右蓝(新),颜色固定不混用
	数字变化用大字号 + 箭头("5% → 3%" 用大字号)
	时间节点强调"几月几号开始"——用日期徽章样式
	配色避免红色(避免暗示"政策不好"),多用蓝色和绿色
	
热点事件	结构 1:时间线推演(Chronological Timeline)
	适用场景:有明确发生顺序的事件(如"某公司爆雷全过程"、"某政策从提出到落地")
	卡片骨架(6-12 张):
	
	[1] 事件总览:一句话概括 + 关键日期

	结构 2(普通用户):一句话结论 + 关我什么事(Lin-Style Explainer)

	设计参考:小 Lin 说的财经科普风格——把复杂研究用日常类比讲清楚

	[1] 论断卡(Hook):一句话核心观点 + 反直觉钩子

	[7] 行动建议或启示:读者能拿走什么

	[7] 当前结论:作者目前的看法

多结果	结构 1:多视角共识 + 分歧(Consensus-Disagreement Map)
	适用场景:同一话题下多个信源观点的综合(如"AI 监管:各方怎么看")
	卡片骨架(6-9 张):
	
	[1] 信源概览卡:本图基于 N 个信源 + 信源类型分布(权威/媒体/专家/网友)
	[2] 主题陈述:大家在讨论什么问题
	[3] 共识 1:多数源认同的事实/观点 + 列出支持源 [1][2][3]
	[4] 共识 2:同上
	[5] 分歧点 1:观点 A vs 观点 B(并列展示,各列支持源)
	[6] 分歧点 2:同上
	[7] 待澄清:仍未达成共识 / 缺乏证据的问题
	[8] 综合判断:基于权威性和时效性的可能性评估(谨慎措辞)
	[9] 完整信源列表卡:所有源的标题 + URL + 发布时间
	
	结构 2:综合时间线(Multi-Source Timeline)
	适用场景:基于多个新闻源拼接完整事件脉络(如"某公司近半年发生了什么")
	卡片骨架(7-10 张):
	
	[1] 事件概览:综合自 N 个源 + 时间跨度
	[2] 时间线主轴卡:所有关键事件按时间排列(核心视觉卡)
	[3-N] 每个时间节点的详细说明:
	        每张卡 = 一个时间点 + 该时间点的事件描述
	        在卡片右下角标注信息源 [1][2]
	[N+1] 信息缺口卡(可选):标注哪些时间段没有公开信息
	[N+2] 信息冲突卡(可选):不同源对同一事件的不同说法
	[N+3] 信源列表卡

4.5 内容生成规则(Workers 模块)
4.5.1 文案 (Worker A)
通用规则:
1. 严格遵守字数上限(标题 ≤ 18 字,正文 ≤ 80 字),超出则系统驳回不接受
2. 不得逐字复制原文超过 15 字的连续片段
3. 不得添加原文未出现的事实、数字、观点
4. 不确定信息必须用"或/可能/据报道/作者认为"等限定词
专业用户文案规则:
- 保留专业术语,不强行通俗化
- 关键数字保留精度(如"5.247%"不要写成"约 5%")
- 引用研究时保留来源("根据 X 大学 2024 研究")
普通用户文案规则:
- 专业术语首次出现时附通俗解释("调峰辅助服务(电网平衡机制)")
- 数字尽量做"日常化对比"("相当于 3 个三峡发电量")
- 标题使用悬念句式或行动号召句式

防标题党规则
以下内容严禁出现在标题中:
禁止类型
示例
极端化表述
"震惊!""惊呆了""崩了""炸锅"
制造焦虑
"再不看就晚了""90% 的人都不知道"
虚假悬念
"结局令人意想不到""你绝对想不到"
钓鱼诱导
"看完不收藏后悔"
判定方式:Worker A 输出后,Evaluator 在 Gate 1 阶段对每张卡片标题做关键词检查 + LLM 复核。
防标题党两阶段判定
防标题党检查由 Evaluator 在 Gate 1 阶段对每张卡片的标题执行（Worker A 输出后，Blueprint 进入 Gate 1 时）。采用两阶段判定流程：
Worker A 生成标题 → 阶段 1：关键词命中检查 → 阶段 2：LLM 标题党倾向评分 → 判定
阶段 1：关键词命中检查（规则层）
对标题做字符串精确匹配 + 正则匹配，命中以下任一关键词或模式 直接判定为标题党，不进入阶段 2：
暂时无法在飞书文档外展示此内容
判定结果：命中 → clickbait_detected，跳过阶段 2，直接进入"不通过处理"。
关键词表的维护：从一个初始版本起步，通过线上 case 持续扩充，作为可配置文件维护，不写死在代码里。
阶段 2：LLM 标题党倾向评分（语义层）
阶段 1 未命中的标题进入 LLM 复核。LLM 输出结构化结果：
json
{
  "clickbait_score": 35,
  "verdict": "borderline",
  "issues": ["过度悬念"],
  "rewrite_suggestion": "中国新能源消纳率达 96.7%，部分省份仍承压"
}
字段说明：
字段	含义	取值
clickbait_score	标题党倾向分（0-100）	0 = 完全中性陈述；100 = 极端标题党
verdict	三档判定	clean / borderline / clickbait
issues	命中的问题类别	数组，可多选：过度悬念/制造焦虑/极端化/空话/无信息量
rewrite_suggestion	改写建议	仅当 verdict ≠ clean 时输出

判定阈值：

clickbait_score	verdict	处理
0–25	clean	通过
26–60	borderline	警告，附 rewrite_suggestion，不强制驳回但记录
61–100	clickbait	驳回

Voting 模式：调用 LLM 3 次取众数（或分数取中位数），减少单次抖动导致的误判。
不通过处理流程

触发条件	处理动作	单卡重试上限
阶段 1 命中	自动驳回 → Worker A 重写（prompt 中告知命中的关键词）	2 次
阶段 2 verdict = clickbait	自动驳回 → Worker A 重写（prompt 中附 issues + rewrite_suggestion）	2 次
阶段 2 verdict = borderline	不驳回，但在 Blueprint 中标记 title_warning，进入 Gate 1 整体评分时影响"卡片合理性"维度	—
同一卡片标题重写 ≥ 2 次仍不通过	强制改写为陈述式标题模板（"{主体}：{核心动作}{核心数字}"），不再调用 Worker A	—

陈述式标题模板示例（兜底用）：
政策类："{政策名称}：{生效时间}起施行"
数据类："{主体}{指标}{数字}，{时间}"
事件类："{主体}{动作}：{时间}"
兜底模板由系统直接根据卡片内容字段拼接，保证一定能输出可用标题，不会因标题党问题阻塞整个 Blueprint。
与 Gate 1 评分的关系
阶段 1/2 都是前置检查，独立于 Gate 1 的 4 维评分
但 title_warning 状态会扣减 Gate 1 的"卡片合理性"分数：每张 borderline 标题扣 5 分
这样 borderline 不强制驳回单卡，但累积过多 borderline 会拖累 Gate 1 整体不通过，触发整体回退
性能与成本

阶段	调用	平均耗时	成本
阶段 1（关键词）	无 LLM	< 10ms / 卡	0
阶段 2（LLM）	仅阶段 1 未命中的卡片	~ 1-2 秒 / 卡（含 voting）	取决于卡片数

优化点：阶段 2 可以批量调用——把 Blueprint 中所有阶段 1 未命中的标题一次性传入 LLM，让其输出每个标题的评分数组。这样 N 张卡只调一次 LLM。
4.5.2 事实核验 (Worker B)
4.5.2.1 职责定义
Worker B 是 生成时的内联校验器，对 Worker A 输出的每张卡片做元素级、机械式的事实比对。它的目标是确保每张卡片中出现的可枚举事实元素都能在原文中找到精确出处。
Worker B 不做语义判断、不调用 LLM 做整体复审，这些工作交给 Gate 1。
4.5.2.2 校验触发时机
Worker A 生成卡片 → Worker B 逐元素校验 → 通过则入 Blueprint / 驳回则回 Worker A
- Worker B 每张卡校验一次，不等到 Blueprint 全部生成
- Worker A 一张卡被驳回 → 单卡重试上限 2 次 → 仍失败则该卡降级为 text_only 摘要卡或整体回退到 Agent 2
4.5.2.3 校验对象（事实元素清单）
Worker B 只校验以下 5 类可枚举元素：

元素类型	示例	校验标准
数字	"5.247%"、"14 亿"、"$23B"	与原文完全一致，不允许四舍五入或精度损失
时间	"2024-03-15"、"2024 年第三季度"	年月日精度与原文一致
人名	"黄仁勋"、"Elon Musk"	姓名用字与原文完全一致（含中英文）
机构名	"国家发改委"、"OpenAI"	全称/简称需与原文匹配
地点	"北京"、"硅谷"	与原文一致

不在校验范围内的内容（交给 Gate 1）：
- 论点的语义改写是否准确
- 卡片间是否存在矛盾
- 原文主旨是否被曲解
- 标题钩子是否合理
4.5.2.4 校验方法（机械式四步法）
对每张卡片的每个 claim：
  Step 1：用规则抽取该 claim 中所有事实元素
          - 数字：正则匹配 \d+(\.\d+)?[%亿万千人倍]?
          - 时间：正则匹配 YYYY-MM-DD / YYYY 年 / Q[1-4]
          - 命名实体：调用 NER 工具抽取人名/机构/地点
  
  Step 2：在原文中**字符串精确搜索**每个元素
          - 数字必须字符精确匹配
          - 命名实体允许全称↔简称映射（需在 entity_alias 表中预注册）
  
  Step 3：判定 4 类结果
          - exact_match：原文中存在完全一致的元素 → 通过
          - alias_match：通过别名表匹配（如"发改委"↔"国家发改委"）→ 通过，标记 alias_used
          - precision_loss：原文是 "5.247%"，卡片是 "约 5%" → 驳回
          - no_evidence：原文中找不到该元素 → 驳回
  
  Step 4：输出 evidence_span
          - 通过的每个元素必须挂载 evidence_span（原文字符位置 + 上下文 50 字）
          - 此 span 直接写入 Blueprint，供 Gate 1 复用，避免重复检索
关键设计：Worker B 不调用 LLM 做语义判定。这一层只做规则匹配和字符串比对，响应时间 < 500ms / 卡，成本几乎为零。
4.5.2.5 强制驳回规则
任一元素出现以下情况，该卡片直接驳回，不进入 Blueprint：


情况	处理
数字精度损失（"5.247%"→"约 5%"）	驳回，要求 Worker A 保留原始精度
数字单位被擅自换算（"14 亿元"→"$200M"）	驳回
人名/机构名与原文不符	驳回
时间精度变粗（原文"2024-03-15"→卡片"2024 年初"）	驳回
任一元素 no_evidence	驳回，要求重写或删除该元素

Worker B 通过的卡片，会在 Blueprint 中附加 b_check 字段：
json
{
  "card_id": "card_03",

}

4.5.3 内容结构 (Worker C)
职责定义
Worker C 必须为 Blueprint 中的每一张卡片产出 visual_spec 对象。这个对象包含 4 个核心决策:
决策项	说明
视觉类型(visual_type)	这张卡用什么图形形式呈现(8 种可选)
结构化数据	视觉类型对应的具体数据(如流程图的节点和边)
视觉重点	这张卡上要重点强调什么内容
辅助元素建议	是否需要 icon / 配图,关键词是什么
Worker C 不输出 SVG/HTML 代码——它只输出"该长什么样"的指令,真正绘制由模板化代码完成。
八种视觉类型
每张卡片的 visual_type 必须从以下 8 种中选一种:

视觉类型	中文名	适用场景	必须包含的字段
text_only	纯文字卡	金句、引用、过渡卡	标题 + 正文
text_with_icon	文字+图标	普通论点卡(默认选择)	标题 + 正文 + 图标关键词
data_highlight	数据高亮	单个关键数字的强调	主数字 + 单位 + 一句话解释
data_chart	数据图表	多数据点的可视化	图表类型 + 数据数组
timeline	时间线	时间序列内容	时间节点数组 + 节点描述
flow_diagram	流程/因果图	步骤、流程、因果关系	节点数组 + 边数组(含关系标签)
comparison_table	对比表	多对象对比	维度列 + 对比项数据
entity_graph	关系网	多主体关系	节点数组 + 边数组(含关系类型)


3.3 视觉类型的选择决策树
Worker C 拿到一张卡片时,按以下决策树选择 visual_type:
该卡片包含的内容...
├─ 是单一引用、金句或过渡内容?
│  └─ ✅ text_only(纯文字)
│
├─ 含 1 个核心数字,且这个数字本身就是结论?
│  └─ ✅ data_highlight(数据高亮)
│
├─ 含 ≥ 2 个数字且可比较?
│  ├─ 数据点 ≤ 5 个 → ✅ data_chart(图表类型:饼图)
│  ├─ 数据点 6-15 个 → ✅ data_chart(图表类型:柱状图)
│  └─ 数据点 > 15 个 → ✅ data_chart(图表类型:折线图)
│
├─ 含 ≥ 3 个时间点?
│  └─ ✅ timeline(时间线)
│
├─ 描述步骤、流程或因果关系?
│  └─ ✅ flow_diagram(流程图)
│
├─ 含 ≥ 3 个实体且实体间有关系?
│  └─ ✅ entity_graph(关系网)
│
├─ 含 ≥ 2 个对象的并列对比?
│  └─ ✅ comparison_table(对比表)
│
└─ 以上都不是?
   └─ ✅ text_with_icon(文字+图标,默认)
关键决策原则:优先选择信息密度更低的类型——同样能表达一个内容,优先选 text_with_icon 而不是 flow_diagram。Worker C 应该是"内敛"的,而不是"炫技"的。
3.4 各视觉类型的具体规则
规则 1:text_only 纯文字卡
用途:开场金句、章节过渡、收尾感悟
规则:

项	规则
字数下限	标题 ≥ 8 字(太短显得空)
字数上限	标题 ≤ 18 字,正文 ≤ 60 字
强制要求	必须有视觉重点(整句加重 / 关键词高亮)
配图	不允许放图标(避免削弱文字感染力)

反例:不要用纯文字卡承载有数据或多个论点的内容。
规则 2:text_with_icon 文字+图标
用途:大部分常规论点卡(系统默认选择)
规则:

项	规则
字数	标题 ≤ 18 字,正文 ≤ 80 字
图标数量	1 个(必须是单一图标,不是组合插画)
图标位置	标题前 / 标题上方,不抢主体位置
图标关键词	必须输出 3 个候选(如 ["lightning", "energy", "power"])

关键约束:图标只是"装饰锚点",不承载信息。如果图标信息量大于文字,应改用其他视觉类型。
规则 3:data_highlight 数据高亮
用途:强调单一关键数字(如"GDP 5.2%"、"投资回报 23 倍"、"覆盖 14 亿人")
规则:

项	规则
主数字位置	卡片中央或上半部,占视觉面积 ≥ 40%
单位	必须明确标注(% 亿 人 倍)
上下文文字	≤ 25 字,放在数字下方,解释"这个数字意味着什么"
趋势指示	可选(↑ ↓ →),仅当有明确趋势时使用
来源标注	必填,小字号放在卡片底部


强制规则:数字必须 100% 来自原文,不允许 Worker C 估算、推断或四舍五入。
规则 4:data_chart 数据图表
用途:多数据点对比、趋势展示
子类型选择:
图表子类型

图表子类型	使用条件
饼图	部分-整体关系,数据点 2-5 个
柱状图	类目对比,数据点 3-10 个
折线图	时间序列趋势,数据点 ≥ 5 个
散点图	双变量关系(P1+ 不在 MVP)
面积图	累计趋势(P1+ 不在 MVP)

面积图
累计趋势(P1+ 不在 MVP)
数据规则:

项	规则
数据点数	单图表 ≤ 15 个数据点(超出则拆图)
单位一致性	同一图表中所有数据必须同单位
数据出处	每个数据点必须挂载 source_in_original
坐标轴	X/Y 轴标签必须来自原文,不可自创
标题	图表标题 ≤ 20 字,概括图表内容

强制规则:Worker C 不能"美化"数据——例如不能把"5.247%"渲染成"约 5%"以求美观。
规则 5:timeline 时间线
用途:有明确时间序的事件、政策推进、技术演进
规则:

项	规则
时间点数	3-8 个(少于 3 个用文字表达更好,多于 8 个考虑分卡)
时间精度统一	同一时间线内,精度统一(全到月或全到日,不混用)
时间格式	YYYY-MM-DD 或 YYYY 年 MM 月,禁止"约一周后""不久之后"模糊表述
节点描述字数	≤ 20 字
关键节点标注	起点 / 转折点 / 当前点必须特殊标记
方向	默认从左到右(横版)或从上到下(竖版)

规则 6:flow_diagram 流程/因果图
用途:步骤、机制、因果链
规则:

项	规则
节点数	3-7 个(超出则拆图或简化)
节点字数	每节点 ≤ 8 字
边的关系标签	必须明确(导致 / 需要 / 形成 / 激励 / 触发 等),不允许无标签连接
流向	单向流(避免循环图,除非内容确为循环)
分支	≤ 2 个分支(超出则结构过于复杂,应改用其他视觉类型)

规则 7:comparison_table 对比表
用途:多对象的并列对比
规则:

项	规则
对比对象数	2-4 列(超 4 列竖版画布会拥挤)
对比维度	3-6 行(少于 3 行对比意义不足,多于 6 行信息过载)
单元格字数	每格 ≤ 12 字
维度标签	第一列必须是维度名称
视觉差异	推荐对比对象用不同底色或边框区分
表头	必须有,且要清晰区分(粗体或异色)

规则 8:entity_graph 关系网
用途:多主体关系展示(如收购案各方、产业链上下游)
规则:

项	规则
节点数	3-8 个(超出则关系图过于复杂)
节点分类	不同类型主体用不同视觉编码(颜色 / 形状)
边的关系	必须有明确关系标签(投资 / 起诉 / 合作 / 竞争)
立场标注	如适用,用颜色区分立场(支持 / 反对 / 中立)
中心节点	推荐有 1 个中心主体,其他围绕

3.5 全局规则(跨视觉类型)
无论选择哪种视觉类型,以下规则全局生效:
规则 G1:视觉多样性约束
同一 Blueprint 内,不同卡片的 visual_type 必须满足:
  - 至少有 3 种不同类型
  - 同一类型连续出现 ≤ 3 张
  - text_with_icon 类型占比 ≤ 60%(避免视觉同质化)
违反时的处理:Worker C 必须主动调整某些卡片的 visual_type,而不是全用默认 text_with_icon。
规则 G2:数据可追溯性
任何视觉类型中出现的数字、时间、人名、机构名:
  - 必须能在 source_text 或 claim.evidence_span 中找到原文出处
  - 必须挂载到对应的 claim 或 data_point 对象
  - 不允许 Worker C 自行加工(如百分比四舍五入、单位换算)
规则 G3:视觉重点强制
每张卡片必须显式标注 emphasis(视觉重点):
  - highlight_number:强调某个数字
  - highlight_phrase:强调某个短语
  - highlight_node:强调流程图/关系图中的某个节点
  - none:本卡无重点(仅 text_only 类型可选)
视觉重点最多 1 个,严禁"全场高亮"。
规则 G4:辅助元素建议
每张卡片可附辅助元素建议(可选):
  - suggested_icons:推荐图标关键词,3 个候选
  - illustration_keywords:推荐插画关键词(P1+,MVP 不启用)
Worker C 只输出关键词,不输出实际图片。

4.7 蓝图信息评估gate1
4.7.1 Gate 1 的定位
Gate 1 是 Blueprint 全量生成完成后的整体复审层，工作在卡片间和Blueprint 全局两个层级。
Gate 1 不重复 Worker B 已经做过的元素级校验——所有进入 Gate 1 的卡片，其 b_check.status 必为 passed，元素级事实正确性已被保证。
Gate 1 关心的是机械式校验抓不到的"软问题"：
- 改写后的语义是否仍忠于原文
- 卡片之间是否互相矛盾
- 整体叙事是否曲解了原文主旨
- 卡片数量、信息分布是否合理
- 文案是否匹配目标用户画像
4.7.2 与 Worker B 的职责边界
  维度	Worker B（已完成）	Gate 1（本层职责）
检查对象	单卡内的事实元素（数字/时间/人名等）	卡片整体语义、卡间关系、全局叙事
检查方法	字符串/数值精确匹配	LLM 语义判定
调用成本	无 LLM，规则匹配	调用 LLM，4 个维度并行
输入信任前提	直接读 Worker A 输出	信任 b_check 已通过，不重复元素核验
失败处理	单卡驳回，回 Worker A 重写	Blueprint 整体回退，回 Orchestrator 重新调度

简记：Worker B 防"写错事实"，Gate 1 防"歪曲原意 + 结构失当"。
4.7.3 四维评分
Gate 1 对 Blueprint 整体并行执行 4 个维度的评估，每个维度独立 LLM call（Voting 模式，3 次投票取众数）：

维度	阈值	评估对象	评估方法
信息完整度	≥ 85 分	Blueprint vs 原文骨架	LLM 比对：原文核心论点有多少被卡片覆盖；遗漏的是否为关键信息
语义忠实度	≥ 90 分	每张卡的改写文本 vs 其 evidence_span	LLM 判定：卡片表述是否扭曲原文语义、是否过度引申、是否丢失限定条件
卡片合理性	≥ 80 分	Blueprint 整体结构	检查卡片数量是否符合 4.3.2 规则、信息分布是否均衡、叙事流畅度、卡间是否矛盾
受众适配度	≥ 75 分	文案语言风格 vs RouterDecision.user_type	抽样检查文案术语密度、句式复杂度是否匹配目标画像

关键变化：
- 原来的 "事实一致性 ≥ 95 分" 改为 "语义忠实度 ≥ 90 分"——不再做元素级比对（那是 Worker B 的事），而是判断改写是否扭曲了语义
- 阈值从 95 降到 90，因为语义判定本身有主观性，过严会导致大量假阳性回退
4.7.4 语义忠实度的具体判定标准
这是 Gate 1 最核心也最容易出歧义的维度，需要明确判定标准：

判定结果	标准	示例
忠实	改写后核心语义不变，限定词完整	原文"可能在 2025 年实现"→卡片"预计 2025 年实现"（保留不确定性）
弱化偏离	丢失关键限定词但主旨未反	原文"在特定条件下可能下降 5%"→卡片"会下降 5%"（丢失"特定条件"）
严重偏离	主旨反转、过度引申、强加因果	原文"两者相关"→卡片"A 导致 B"（相关 → 因果）

- 弱化偏离：扣分但不强制驳回，单项 ≥ 90 分仍可通过
- 严重偏离：单卡严重偏离即整体不通过，直接回退
4.7.5 跨卡一致性检查（卡片合理性维度的子项）
这是 Worker B 不可能发现的问题，必须由 Gate 1 处理：
对 Blueprint 中所有卡片做两两比对：
  - 同一指标在不同卡片是否出现矛盾数值
    （例：卡 3 写"增长 5%"，卡 7 写"增长 7%"——若原文只有一个数据，必有错）
  - 同一主体在不同卡片是否出现立场矛盾
    （例：卡 2 说"A 公司支持该方案"，卡 5 说"A 公司反对该方案"）
  - 时间线是否前后矛盾
    （例：卡 4 说事件 X 发生在 2023 年，卡 8 说 X 发生在 2024 年）

发现矛盾 → 卡片合理性维度直接判 0 分 → Gate 1 不通过
4.7.6 通过条件与失败处理
通过条件：4 项全部达到阈值。
失败处理：

失败维度	回退目标	回退指令
信息完整度 < 85	Agent 2（内容理解）	提示遗漏的核心论点列表，要求重新分块/补充
语义忠实度 < 90	Worker A（通过 Orchestrator）	提示具体偏离的卡片 ID + 原文 span，要求重写
卡片合理性 < 80	Agent 3（Orchestrator）	提示卡片数量/分布/矛盾问题，要求重新规划 Blueprint
受众适配度 < 75	Worker A	提示用户画像不匹配的卡片，要求调整语言风格

注意：Gate 1 的失败回退不绕过 Worker B——回退后重新生成的卡片仍需经过 Worker B 元素级校验，再进入 Gate 1。
4.7.7 性能预期
- Worker B（已完成）：< 500ms / 卡，无 LLM
- Gate 1：4 个维度并行，单维度 LLM call ~ 3-5 秒，总耗时 ~ 5-8 秒（不含 voting 多次调用）
- voting 模式（每维度 3 次）→ 总耗时 ~ 15-20 秒
成本控制：因为 Worker B 已经把元素级问题挡在外面，Gate 1 的 LLM 只判定语义，prompt 中无需附带原文全文——只需附带每个 claim 对应的 evidence_span（Worker B 已挂载），可大幅降低 token 消耗。
4.8 分流决策
判断步骤如下，需要逐步按照顺序判断，比如某长文在step2判断为视频后，用step3可以再判断为图，此次内不需要综合考虑step1、2、3，也不要循环判断。
step1：默认生成图
step2：更改为视频：满足如下任一条件更改为视频
1. 文章含强时间序(时间锚点 ≥ 5 个),且时间跨度跨越多年
2. 用户偏好设置中明确选择"视频"
3. 文章长度 > 8000 字 且 长文类型为时间线或者效果影响类型
step3：更改为图：满足如下任一条件更改为图
1. 文章长度 < 1500 字(视频太短不值得)
2. 文章信息密度 > 0.8(每千字 ≥ 8 个核心数据点),视频展示数据反而不如图直观
3. 文章类型为 通知政策，政策类不适合做娱乐化视频
4. 风险评估为 high(避免视频形式放大错误传播)

4.11 渲染评估gate2
4.11.1 Gate 2 的定位
Gate 2 是 渲染产物的最后一道质检，工作在像素级和视觉级两个层面。任何渲染问题（文字溢出、错别字、事实漂移）都在这里被发现并触发回退。
Gate 2 与 Gate 1 的本质差异：
维度	Gate 1（蓝图评估）	Gate 2（渲染评估）
检查对象	结构化数据（Blueprint JSON）	渲染产物（PNG / MP4）
检查方法	LLM 语义判定	OCR + Vision LLM + DOM 检测
关心问题	内容是否偏离原文	渲染是否忠实呈现 Blueprint
4.11.2 五项检查（不变）
沿用原 PRD 的 5 项检查：文字溢出、字号可读性、错别字、视觉合理性、事实漂移。任一不通过 → Gate 2 整体不通过 → 进入回退流程。
4.11.3 问题分类与回退目标
Gate 2 不通过时，根据问题类型分类回退。问题类型由 Gate 2 自身判定（每个失败检查项必须输出 issue_type 字段）：
issue_type	触发条件（举例）	回退目标	严重程度
render_only	文字溢出、字号偏小、布局拥挤	Tool 1 / Tool 2（渲染工具）	低
blueprint_level	单卡信息量超限、视觉类型与内容不匹配、卡间风格冲突	Agent 3（Orchestrator）→ 重新生成 Blueprint	中
fact_drift	OCR 提取的图中文字 ≠ Blueprint 文本（含错别字、数字漂移）	Agent 2（Content Understanding）→ 完整重做	高
多重问题同时出现时：按严重程度从高到低优先处理。例如同时检测到 fact_drift 和 render_only → 先按 fact_drift 回退（因为重做 Blueprint 后 render 也会重做）。
4.11.4 重试预算分配机制
核心原则：分层硬上限 + 全局总闸 + 优先级抢占。
预算分配表：
层级	单层重试上限	单次重试成本（约）	累计耗时上限
render_only	3 次	~10 秒	~30 秒
blueprint_level	2 次	~30 秒	~60 秒
fact_drift	1 次	~90 秒（重走 Agent 2 + Agent 3 + 渲染）	~90 秒
全局总和	6 次	—	~3 分钟
变更说明：
- 原 PRD 的"全局 8 次"改为 "全局 6 次"，即各层上限之和（3+2+1）
- 取消"先到先得"或"软共享"的歧义，改为严格分层独立计数
- 每个 issue_type 维护独立的重试计数器，互不挤占
4.11.5 重试计数规则（消除歧义）
关键规则：
1. 每个 issue_type 独立计数
  - render_only 重试 3 次 ≠ 占用 fact_drift 的额度
  - 各计数器初始值为 0，触发该类回退时 +1
2. 同一次回退只占一个层级的额度
  - 即使一次失败同时命中 fact_drift 和 render_only，按优先级判定为 fact_drift，只扣 fact_drift 的额度
  - 因为高层级回退（如重做 Blueprint）必然会重做低层级（重新渲染），不重复计数
3. 任一层级用完即触发降级，不向其他层级"借额度"
  - render_only 已用 3 次仍不通过 → 不允许继续在渲染层重试 → 升级为 blueprint_level（如还有额度）或直接降级输出
  - 这样避免"render_only 把 fact_drift 的额度吃掉"的情况
4. 高层级回退会重置低层级计数器
  - 触发 fact_drift 回退后，blueprint_level 和 render_only 计数器清零
  - 因为重新生成的 Blueprint 是全新内容，之前的渲染失败经验已不适用
  - 同理，触发 blueprint_level 回退后，render_only 计数器清零
5. fact_drift 用完 1 次仍失败 → 直接进入 L3 全面降级
  - 不再尝试任何层级
  - 因为 Agent 2 重做仍出现事实漂移，说明问题在原文理解层面，无法通过重试解决
4.11.7 降级输出策略（修订）
降级触发条件改为与重试计数器挂钩，更明确：
降级层级	触发条件	输出内容
L1 微降级	render_only 计数器达 3 且无法升级	输出当前最优渲染版本 + 角标"渲染优化中"
L2 部分降级	blueprint_level 计数器达 2 且无法升级到 fact_drift（或 fact_drift 已用完）	反复失败的卡片改为"信息密度较低，建议参考原文第 X 段"；其他卡片正常输出
L3 全面降级	fact_drift 计数器达 1 仍失败，或 任何层级触发 ≥ 5 次累计失败	输出"图文摘要"（纯文字 + 1 张概览图）+ 原文链接 + 失败原因说明
4.11.8 极端情况兜底
情况	处理
渲染工具自身崩溃（非 Gate 2 不通过）	不消耗任何重试额度，直接走渲染工具的失败处理（4.9.1.6）
同一卡片连续 3 次触发 fact_drift（理论上不可能，因为 fact_drift 上限为 1）	系统级告警 + L3 降级
总耗时超过 5 分钟（兜底超时）	强制 L3 降级，不论计数器状态
